# Tamil learning API

The web client uses authenticated `/api/tamil` routes. `GET /catalog` returns 263 catalog items (`vowel`, `consonant`, `uyirmei`, `word`, `sentence`). Items expose a stable `id`, Tamil `text`, practice metadata, and an `audio_url` only when a validated local example exists. `can_evaluate: false` means the app must not show an acoustic pronunciation score.

`POST /answer` accepts `{ "item_id": "word-amma", "selected_id": "word-amma", "prompt_type": "audio_recognition", "request_id": "<UUID>" }`. Valid prompt types are `character_recognition` for letters, `text_recognition` for words/sentences, and `audio_recognition` only when the target item has local audio. The server checks that the selected item exists and is of the same kind, grades it by catalog ID, and saves one result per user/request UUID. A repeat of the same request returns `already_saved: true`; changing an existing request returns HTTP 409. The web client reuses the same UUID when it retries a lost response for the same answer. A recognition answer is never reported as a microphone or phoneme score.

The same route also accepts `meaning_matching` for words and sentences with `selected_id`, and two exercises with `selected_ids`: `uyirmei_composition` takes `["consonant-ka", "letter-aa"]` for target `uyirmei-ka-aa`; `sentence_ordering` takes a permutation of zero-based word indexes, such as `["0", "1", "2"]` for the three-word `sentence-amma-veettil`. The server rejects unknown components, missing or duplicate word positions, changed idempotent replays, and exercises on the wrong content kind. These saved exercises use `catalog_exercise_v1` and remain unscored acoustically. For backward compatibility, the progress API's `recognition_*` counters cover all server-graded selection and construction activities.

`text_writing` accepts `written_text` (at most 200 characters) for any catalog item. It grades the user's Tamil script against the authoritative item text after NFC normalization and harmless punctuation/spacing cleanup; it preserves word boundaries and letter differences. The typed answer is bounded, normalized, saved, and included in replay conflict checks. This is keyboard text entry, not handwriting recognition.

Tamil speech transcripts use the same boundary-preserving normalization before comparison. A saved speech-text result is correct only when its normalized Tamil text exactly matches the catalog target. Changing a content word, a Tamil character, or a word boundary cannot grant completion even when the character edit distance is small; harmless punctuation and repeated spaces remain ignored. The original transcript and character similarity remain available for partial feedback. New results use `tamil_text_similarity_v2`.

`POST /evaluate` accepts a bounded audio upload, item ID, and UUID request ID. It returns a scorable acoustic result only when the relevant evaluator can support one; an unavailable or uncertain evaluator produces an explicit unscored result. `GET /progress` aggregates microphone scores separately from recognition attempts and correct answers. `recognition_by_item[id]` provides attempts, correct attempts, accuracy, and mastery after three correct answers. `completed_items` records lessons with a correct answer or matching acoustic result; `mastered_items` is stricter recognition practice.

`GET /progress` also returns `review_by_item[id]` with `due_at`, `due`, and `interval_days`, plus `review_due_items` sorted by due time. Correct answers return after 1, 3, 7, 14, then 30 days as the count grows; a wrong answer is due immediately. This is a simple repeated-exposure schedule derived from persisted attempt history, not a validated cognitive mastery model. The catalog shows due lessons with links back to their challenge.

The browser loads `audio_url` from its own origin under `/assets/tamil-reference/`. The [audio manifest](../frontend/public/assets/tamil-reference/manifest.json) contains file hashes, source provenance, and licensing. The backend does not serve those WAV files directly.

`GET /health/speech` reports the ONNX acoustic phoneme engine in its top-level `status` and separately reports optional Tamil speech-to-text in `tamil_stt`. That nested status is `ready`, `not_loaded`, `disabled`, or `unavailable` with a bounded reason (`checkpoint_missing`, `runtime_missing`, or `model_load_failed`). The check does not load the large Tamil checkpoint. An acoustic `ready` response alone does not prove Tamil transcription is available; when it is unavailable, word/sentence microphone practice falls back to the acoustic phoneme evaluator.

Deployments that saved older `tamil_text_similarity_v1` attempts can regrade them from their stored transcript with `python scripts/regrade_tamil_text_attempts.py` from `backend`. The default is a read-only aggregate dry run; `--apply` writes `v2` results only for canonical word/sentence attempts and is idempotent. Run it against the same configured database as the API after verifying connectivity. It prints no user identifiers or transcripts.
